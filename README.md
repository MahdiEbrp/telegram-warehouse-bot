# بات تلگرام مدیریت انبار و فروش — نسخهٔ 1.3.0

بک‌اند **Next.js App Router** با TypeScript سخت‌گیرانه، grammY، Drizzle و SQLite/Turso. رابط کاربری کاملاً در تلگرام و با دکمه‌های Inline است؛ تنها دستور، `/start` است. متن فقط برای مقدار فیلدهای ویزارد دریافت می‌شود.

**دامنهٔ پروژه:** یک فروشگاه، چند کاربر مدیریتی و چند نمونهٔ سرور **با Turso مشترک**؛ SQLite فایل محلی فقط برای توسعهٔ تک‌فرایندی است. این نسخه پنل داخلی مدیریت فروش است، نه فروشگاه عمومی مشتریان و نه سامانهٔ چندمستأجری مستقل. ثبت سفارش توسط مدیر انجام می‌شود. تأیید پرداخت و ثبت بازپرداخت **دستی و حسابداری** هستند؛ درگاه واقعی یا انتقال وجه پیاده‌سازی نشده است.

## جدید در 1.3: فرم تک‌فیلدی + آزمون بار قابل بازتولید

- **تمام ۱۱ ویزارد** به موتور مشترک تایپ‌شده منتقل شده‌اند: یک فیلد در هر پیام، قبلی/بعدی/انصراف و مرور نهایی؛ متن فقط مقدار فیلد است.
- **قبلی واقعی با پیش‌نویس پایدار:** نام، عدد، گزینه و سبد حفظ می‌شوند؛ بازگشت از مشتری به سبد، سفارش را از اول نمی‌سازد. تغییر وابستگی مثل شناسهٔ مشتری/شرکت حمل، فیلدهای وابسته را عمداً نامعتبر/پاک می‌کند.
- **انتخاب + بعدی جدا:** فقط انتخاب گزینه، مرحله را رد نمی‌کند. دکمهٔ بعدی بدون مقدار معتبر واقعاً غیرفعال است و callback جعلی هم آن را دور نمی‌زند.
- **رابط بومی تلگرام:** کارت و پیشرفت فارسی، رنگ‌های native، داشبورد نقش‌محور و یک کیبوردِ منطقی فعال؛ پنل روی دکمه‌ها edit می‌شود و پس از تایپ کارت تازه می‌آید.
- **سبد کاربردی‌تر:** ویرایش تعداد، حذف قلم، ادغام کالای تکراری و تازه‌سازی صریح قیمت/موجودی؛ هیچ رزروی پیش از تأیید نهایی انجام نمی‌شود.
- **سخت‌سازی نشست:** nonce رمزنگارانهٔ ۱۲۸ بیتی، توکن هر رندر، اتصال به کاربر/چت/پیام، رد update دیررسِ خارج از ترتیب، سقف ۳۰۰ تعامل و ثبت receipt برای رد دسترسی دائمی.
- **شواهد، نه امتیاز تضمینی:** آزمون آفلاین **۵۰ کاربر / ۵۰۰۰ آپدیت** و آزمون رقابت موجودی ۵۰طرفه؛ گزارش تأخیر/خطا/منابع و ۲۰ invariant. [گزارش بار](docs/STRESS_TEST.md) · [راستی‌آزمایی](docs/VERIFICATION.md).
- **پیش‌نمایش قابل بازتولید رابط:** [HTML مستقل](docs/ui-preview.html)، ۱۲ نمای گرفته‌شده از کد در TestBot؛ قاب/رنگ، تقریب آفلاین‌اند و screenshot کلاینت تلگرام نیستند.
- schema نسبت به v1.2 تغییر نکرده است؛ env پیشنهادی conversation اکنون `4` و namespace کدی `:forms-v3` است. [قواعد ویزارد](docs/WIZARDS.md) · [امنیت و مرز تضمین‌ها](SECURITY.md).

## قابلیت‌های v1.2 که حفظ شده‌اند

- **چند مرسوله برای هر سفارش** با شمارهٔ پایدار، بارکد/شرکت/هزینه و وضعیت مستقل؛ سقف ۲۰ مرسولهٔ جاری. حذف پیش‌نویس، شمارهٔ آن را دوباره مصرف نمی‌کند.
- **ارسال/تحویل مستقل** و به‌روزرسانی وضعیت کل سفارش وقتی همهٔ مرسوله‌ها به مرحلهٔ لازم برسند؛ لغو پس از ارسال حتی یک مرسوله ممنوع است.
- **Excel واقعی `.xlsx`** از داخل فهرست سفارشات؛ دو sheet فارسی، فیلتر صف/وضعیت/بازه، حفظ صفرهای کد و متن literal بدون فرمول. فقط مدیر/مدیرکل؛ سقف ۱۰۰۰ ردیف و عدم خروجی ناقص.
- **نصب تازهٔ Vercel + Turso** با راهنمای مرحله‌ای، `vercel.json` و فرمان فقط‌خواندنی `npm run deploy:check`؛ انتشار واقعی نیازمند حساب‌ها و secretهای خودتان است.
- **ارتقای آماده و تست‌شده** از v1.0/v1.1، حفظ داده‌های قدیمی و راهنمای backup/rollback.
- قابلیت‌های v1.1 حفظ شده‌اند: **REF کوتاه مستقل از ORD**، کد واقعی پست/شرکت حمل، جستجو، کپی بومی، لینک و audit.
- همچنان **فقط کارکنان**؛ هیچ پنل مشتری، استعلام زندهٔ carrier یا اعلان خودکار مشتری اضافه نشده است.

**برای انتخاب فعلی شما — نصب تازه:** [راهنمای Vercel + Turso](docs/INSTALL_VERCEL_TURSO.md).

**اگر نسخهٔ قبلی را دارید:** [ارتقای امن](docs/UPGRADE.md)؛ DB و `.env` را حذف نکنید و نویسندگان قدیمی را هم‌زمان با migration فعال نگذارید.

مسیر: **سفارشات ← سفارش ← اطلاعات ارسال و رهگیری ← افزودن/انتخاب مرسوله**. ثبت مشخصات حمل به‌تنهایی وضعیت سفارش را تغییر نمی‌دهد. [جزئیات چندمرسوله و Excel](docs/PARCELS_AND_EXPORT.md) · [قواعد کد و رهگیری](docs/TRACKING.md).

## شروع سریع

پیش‌نیاز: **Node.js 24.x** و npm. Vitest 5 به Node جدید نیاز دارد.

```bash
cd telegram-warehouse-bot
npm ci
cp .env.example .env
# .env را با توکن واقعی BotFather، شناسهٔ عددی مدیرکل و secret تصادفی تکمیل کنید.
# تولید secret: openssl rand -hex 32
npm run db:migrate
npm run db:seed
npm run dev
```

- توسعه: `http://localhost:3000`؛ مسیر `/api/health` فقط سلامت خود فرایند را نشان می‌دهد، نه اتصال به دیتابیس یا تلگرام.
- `SUPER_ADMIN_TELEGRAM_IDS` باید **قبل از اولین تماس مدیر با بات** تنظیم شده باشد. کاربر تازه با این شناسه به مدیرکل تبدیل می‌شود. بقیهٔ کاربران ناشناس، غیرفعال هستند.
- افزودن شناسهٔ یک کاربر **از قبل موجود** به env، دسترسی او را خودکار تغییر نمی‌دهد. این رفتار مانع برگشت خودکار دسترسی‌های لغوشده است. برای راه‌اندازی/بازیابی آگاهانه، یک بار اجرا کنید:

```bash
npm run admin:bootstrap -- --confirm
```

این فرمان به تمام شناسه‌های env دسترسی مدیرکل می‌دهد و رویداد آن را ثبت می‌کند؛ **هرگز آن را به build یا استقرار خودکار اضافه نکنید.**

## دریافت Webhook محلی

ترمینال دیگری باز کنید؛ یکی از این دو کافی است:

```bash
ngrok http 3000
# یا:
npx localtunnel --port 3000
```

آدرس HTTPS تونل را در `APP_URL` فایل `.env` بگذارید؛ سپس:

```bash
npm run webhook:set
npm run webhook:info
```

حالا در گفت‌وگوی **خصوصی** بات `/start` بفرستید. با تغییر دامنهٔ تونل، Webhook را دوباره ثبت کنید. بعضی سرویس‌های تونل صفحهٔ واسط/ضدربات دارند؛ اگر `webhook:info` خطای غیر JSON یا ۴xx نشان داد، از یک تونل عمومی بدون صفحهٔ واسط استفاده کنید. توکن و secret را در URL یا تاریخچهٔ مرورگر قرار ندهید.

## قابلیت‌های پیاده‌سازی‌شده

- **محصولات:** فهرست صفحه‌بندی‌شده، جستجوی نام/SKU، ویزارد کامل افزودن، ویرایش مشخصات، بایگانی امن به‌جای حذف سابقه؛ دسته‌بندی با والد اختیاری.
- **انبار:** موجودی اولیه، تنظیم با دکمه‌های +/− یا ورودی عددی، گزارش کم‌موجودها و گردش؛ حفاظت در برابر تغییر هم‌زمان موجودی.
- **سفارش:** سبد چندقلمی، اطلاعات مشتری، پیش‌فاکتور، رزرو اتمیک موجودی، شمارهٔ یکتا، چرخهٔ وضعیت، پرداخت دستی و ثبت بازپرداخت دستی.
- **ارسال و رهگیری:** کد REF و چند مرسوله با وضعیت مستقل، شرکت حمل و کد مرسوله، کپی/لینک، جستجو و سابقهٔ تغییر؛ هزینهٔ داخلی حمل به جمع سفارش افزوده نمی‌شود.
- **خروجی Excel مرسوله‌ها:** فقط مدیر/مدیرکل، فیلترهای صف/وضعیت/تاریخ ایجاد سفارش، یک ردیف برای هر مرسوله، hash و audit تولید؛ فایل حساس است و نباید عمومی شود.
- **گزارش:** فروش روزانه و ماهانه، کم‌موجودها و گردش انبار. مبالغ صحیح به **تومان**؛ ماه گزارش، **میلادی** و مرز روزها در `STORE_TIMEZONE` است. عنوان/نمایش تاریخ فارسی است، نه محاسبهٔ ماه شمسی.
- **کاربران:** افزودن/فعال‌کردن، تغییر نقش، غیرفعال‌کردن، مشاهدهٔ فعالیت‌ها و جلوگیری از حذف آخرین مدیرکل فعال.
- **تنظیمات:** نام، تلفن، نشانی و راهنمای روش‌های پرداخت فروشگاه.
- **Serverless:** ذخیرهٔ ویزارد در دیتابیس، نسخه‌بندی و انقضا، قفل اشتراکی کاربر/چت، receipt آپدیت و کلید idempotency عملیات.

## نسخه‌ها و دو نکتهٔ سازگاری

نسخه‌های دقیق و `package-lock.json` همراه پروژه‌اند. نسخه‌های اصلی نصب‌شده در این تحویل:

| وابستگی                | نسخه                                            |
| ---------------------- | ----------------------------------------------- |
| Next.js / React        | 16.4.3 / 19.3.1                                 |
| TypeScript             | 5.9.3، با `strict` و `noUncheckedIndexedAccess` |
| grammY / conversations | 1.46.0 / 2.1.1                                  |
| Drizzle ORM / Kit      | 0.45.4 / 0.31.11                                |
| libSQL client / Zod    | 0.18.0 / 4.6.7                                  |
| Vitest / coverage-v8   | 5.0.5 / 5.0.5                                   |
| fflate (XLSX ZIP)      | 0.8.3                                           |
| grammy-test            | 0.1.3                                           |

۱. **App Router روی Vercel نیز Web `Request/Response` دارد.** در این پروژه از `webhookCallback(bot, "std/http", ...)` استفاده شده است، نه رشتهٔ `"vercel"`. در grammY نصب‌شده چنین نام آداپتوری وجود ندارد. نمونهٔ App Router نیز همین آداپتور را به‌کار می‌برد. [2](https://www.launchfa.st/blog/telegram-nextjs-app-router)

۲. در Bot API 10.3، `disabled` از نوع **شیء خالی `DisabledButton`** است، نه `boolean`. دکمهٔ غیرفعال نباید هم‌زمان `callback_data` داشته باشد. پروژه از سازندهٔ type-safe خود grammY استفاده می‌کند: [1](https://core.telegram.org/bots/api#inlinekeyboardbutton)

```ts
new InlineKeyboard().disabled("مرحله بعد ➡️");
// { text: "مرحله بعد ➡️", disabled: {} }
```

## دیتابیس و مایگریشن

برای تعویض محیط، **هیچ کدی تغییر نمی‌کند**؛ تنها دو env زیر عوض می‌شوند:

```dotenv
# محلی
TURSO_DATABASE_URL=file:./data/warehouse.db
TURSO_AUTH_TOKEN=

# ابری، به‌جای مقادیر بالا
# TURSO_DATABASE_URL=libsql://your-database.turso.io
# TURSO_AUTH_TOKEN=your-turso-auth-token
```

```bash
npm run db:migrate    # اجرای مایگریشن موجود؛ تکرار آن امن است
npm run db:seed       # دستهٔ «عمومی» و تنظیمات پیش‌فرض؛ idempotent
# فقط پس از تغییر schema:
npm run db:generate
npm run db:migrate
```

در تست‌ها از `file::memory:` استفاده شده که URL درایور libSQL برای SQLite در حافظه است. در Vercel، SQLite فایل محلی عمداً رد می‌شود؛ ذخیرهٔ پایدار باید Turso با engine سازگار **libSQL** باشد. صف هم‌فرایندی محلی جای تراکنش، قفل دیتابیس یا storage مشترک را نمی‌گیرد. سه مایگریشن آماده در نصب تازه ۱۵ جدول کاربردی می‌سازند. مایگریشن‌ها هنگام دریافت Webhook یا build اجرا نمی‌شوند.

```bash
npm run typecheck
```

تست‌های یکپارچه با **TestBot واقعی پکیج خواسته‌شده** و همان middlewareهای محیط واقعی اجرا می‌شوند؛ تمام درخواست‌های تلگرام شبیه‌سازی می‌شوند. سناریوهای `/start`، فهرست محصول، ویزارد کامل افزودن، callbackها، RBAC، ثبت سفارش، تغییر وضعیت، بازیابی ویزارد پس از ری‌استارت و امنیت Webhook وجود دارند. تست هم‌زمانی موجودی و اطلاعات ارسال از دو client مستقل فایل SQLite در یک فرایند، با صف محلی و تراکنش واقعی استفاده می‌کند؛ این تست ادعای رفتار چندفرایندی یا شبکهٔ ابری نیست. چندمرسوله، فایل XLSX/ارسال سند و preflight نیز تست می‌شوند. مهاجرت از نسخهٔ قبلی با دادهٔ واقعی آزمایشی و حفظ تمام جدول‌های قبلی نیز تست می‌شود. هیچ استعلام واقعی شرکت حمل در تست‌ها انجام نمی‌شود.

## استقرار

۱. پروژه را به Vercel بدهید؛ تنظیمات پیش‌فرض Next.js و Node.js 24 کافی است.
۲. envها را طبق `.env.example` تنظیم کنید؛ در Production از Turso، توکن واقعی بات و secret تصادفی استفاده کنید.
۳. از یک محیط امن با **env همان دیتابیس Production**، `db:migrate` و سپس برای نصب تازه `db:seed` را اجرا کنید. پس از تعیین دامنه، `npm run deploy:check` را اجرا کنید؛ این فرمان فقط‌خواندنی است و deploy نمی‌کند.
۴. بعد از deploy موفق و عمومی‌بودن مسیر Webhook، با `APP_URL=https://your-app.vercel.app`، فرمان `npm run webhook:set` را اجرا کنید.
۵. با `npm run webhook:info` و `/start` در تلگرام وضعیت واقعی را بررسی کنید.
