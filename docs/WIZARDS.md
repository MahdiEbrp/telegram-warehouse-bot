# فرم‌های تک‌فیلدی و نشست پایدار — v1.3

## قرارداد رابط

- هر کارت فقط **یک فیلد قابل تکمیل** دارد. اطلاعات کمکی مثل قیمت/موجودی، سؤال دوم نیستند.
- متن/عدد فقط مقدار همان فیلد است. برای ناوبری، از Inline Keyboard استفاده می‌شود؛ تنها فرمان متنی بات `/start` است.
- «مرحله بعد» با مقدار معتبر فعال می‌شود؛ گزینهٔ انتخابی با ✓ مشخص است و **هنوز به Next جداگانه نیاز دارد**.
- «مرحله قبل» cursor را واقعاً عقب می‌برد؛ مقدار معتبر دوباره تایپ نمی‌شود. در اولین مرحله، قبلی واقعاً disabled است.
- «انصراف»، `/start` یا منوی اصلی، پیش‌نویس را پایان می‌دهند؛ دادهٔ دامنه پیش از تأیید نهایی نوشته نمی‌شود. خواندن داده، احراز هویت/به‌روزرسانی پروفایل و receipt با «ثبت سفارش/محصول» متفاوت‌اند.
- مرور نهایی امکان برگشت دارد. رد قابل اصلاح مثل SKU تکراری، فرم را از ابتدا نمی‌سازد. جستجو فقط‌خواندنی است و تأیید آن دادهٔ فروشگاه را تغییر نمی‌دهد.
- روی دکمه، همان پنل edit می‌شود. پس از تایپ، کارت تازه می‌آید و کیبورد قبلی بازنشسته می‌شود. در خطای دائمی edit، پنل تازه ساخته می‌شود؛ تنها کیبورد آخر از نظر سرور معتبر است، حتی اگر کلاینت نسخهٔ قدیمی را هنوز نشان دهد.

## مسیر هر ویزارد

| Scene                   | فیلدها، سپس مرور                                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------------------- |
| افزودن محصول            | نام ← SKU ← قیمت ← موجودی ← دسته                                                                    |
| ویرایش محصول            | انتخاب یک مشخصه ← مقدار همان مشخصه                                                                  |
| تنظیم انبار             | یک مقدار موجودی با +/− یا ورود عددی؛ سپس تأیید                                                      |
| ساخت سفارش              | سبد با زیرمرحلهٔ کالا/تعداد ← شناسهٔ مشتری ← نام ← تلفن ← نشانی ← توضیحات                           |
| افزودن کاربر            | شناسهٔ تلگرام ← نام ← نقش                                                                           |
| افزودن دسته             | نام ← والد / ریشه                                                                                   |
| تنظیمات                 | نام فروشگاه ← تلفن ← نشانی ← راهنمای پرداخت                                                         |
| جستجوی محصول            | عبارت ← انتخاب نتیجه؛ نتیجهٔ نهایی فقط‌خواندنی                                                      |
| جستجوی سفارش            | عبارت ← انتخاب نتیجه؛ فقط کارکنان مجاز                                                              |
| ثبت/ویرایش ارسال        | روش حمل ← نام شرکت در صورت «سایر» ← کد ← لینک ← کد پستی ← هزینهٔ داخلی ← یادداشت ← علت در صورت لزوم |
| پاک‌کردن پیش‌نویس ارسال | علت ← تأیید؛ فقط پیش‌نویس مجاز                                                                      |

پیشرفت، مرحلهٔ مرور را نیز می‌شمارد؛ مثلاً افزودن محصول ۵ فیلد + مرور = ۶ مرحله. سبد، یک مرحلهٔ اصلی با زیرمرحله‌های مستقل «انتخاب کالا» و «تعداد» است. تعداد کل مراحل حمل با شرط «سایر» و نیاز به علت تغییر می‌کند. نام/مقدار فیلدهای دیگر هم‌زمان درخواست نمی‌شوند.

## حفظ مقدار و تغییر وابستگی

- Back بدون تغییر داده، تمام مقدارهای معتبر قبلی و بعدی را حفظ می‌کند؛ ورودی نامعتبر، جای مقدار معتبر را نمی‌گیرد.
- تغییر آگاهانهٔ شناسهٔ مشتری، **نام/تلفن/نشانی** را پاک می‌کند تا مشخصات شخص قبلی به مشتری تازه نسبت داده نشوند. سبد و توضیحات سفارش باقی می‌مانند.
- تغییر روش حمل، **نام شرکت، بارکد و لینک اختصاصی** را نامعتبر/پاک می‌کند؛ پست/تیپاکس/چاپار/سایر دوباره کد لازم دارند. پیک/حضوری می‌توانند بدون بارکد باشند.
- تغییر عبارت جستجو، نتیجهٔ انتخاب‌شدهٔ عبارت قبلی را پاک می‌کند.
- در ویرایش محصول، پیش‌نویس مقدار هر مشخصه هنگام جابه‌جایی بین گزینه‌ها نگه داشته می‌شود؛ فقط همان مشخصه‌ای که در مرور نهایی انتخاب شده ذخیره می‌شود.
- فیلد اختیاری از Next با مقدار خالی معتبر یا دکمهٔ پاک/بدون‌مقدار پشتیبانی می‌کند؛ `-` نیز در فیلد متنی اختیاری به معنی خالی است.

## سبد و تعارض

سبد تا ۲۰ کالای متمایز دارد. کالای تکراری ادغام می‌شود؛ تعداد هر قلم قابل ویرایش و هر قلم قابل حذف است. برگشت از مشتری، همین سبد را باز می‌کند. تعداد معتبرِ قلم درحال‌ویرایش حتی با Back نگه داشته می‌شود؛ کالای تازهٔ ناتمام تا Next تعداد، به اقلام قطعی سبد اضافه نمی‌شود.

انتخاب/پیش‌فاکتور، موجودی را رزرو نمی‌کند. «به‌روزکردن قیمت و موجودی» یک اقدام صریح است؛ مقادیر quote را تازه می‌کند و اگر تعداد از موجودی کمتر نباشد checkout غیرفعال می‌شود. هنگام ثبت، سرویس تراکنشی دوباره قیمت/موجودی را بررسی می‌کند.

تعارض موجودی دستی بی‌صدا بازنویسی نمی‌شود: با Back، «موجودی تازه» را بخوانید، هدف را تنظیم و دوباره مرور کنید. این دکمه baseline و مقدار پیشنهادی را به عدد تازه برمی‌گرداند. تعارض نسخهٔ مرسوله نیاز به انصراف و بازکردن آخرین اطلاعات دارد؛ صرفاً تازه‌کردن revision برای تحمیل draft کهنه، عمداً انجام نمی‌شود.

## پایداری و مرز امنیت

draft در حافظهٔ دائمی یک سرور نگهداری نمی‌شود؛ conversations v2 آن را از log نسخه‌دار در `bot_conversations` بازسازی می‌کند. I/O و nonce داخل `conversation.external` هستند. نمونهٔ تازهٔ سرور می‌تواند ادامه دهد، مشروط به DB مشترک، نسخهٔ منطبق و نشست منقضی‌نشده.

- nonce: ۱۶ بایت تصادفی / ۱۲۸ بیت، base64url به طول ۲۲؛ callback کمتر از ۶۴ بایت است.
- اعتبار callback: نقش تازه + کاربر/چت + پیام دقیق + nonce + توکن رندر + action مجاز.
- `disabled:{}` تنها action دکمه است؛ جعل callback نیز validation سرور را دور نمی‌زند.
- update ID دیررسِ قدیمی نمی‌تواند مقدار تازه را عوض یا متن فیلد قبل را وارد فیلد بعد کند. به کاربر اخطار داده می‌شود؛ این **صف FIFO/مرتب‌سازی مجدد نیست**.
- سقف هر نشست ۳۰۰ تعامل است، شامل تعامل قدیمیِ دورریخته‌شده. timeout بی‌کاری هر انتظار ۳۰ دقیقه است و اعتبار رکورد storage تا ۲۴ ساعت پس از آخرین نوشتن تمدید می‌شود؛ cleanup برای حذف فیزیکی لازم است.
- `CONVERSATION_VERSION=4` و suffix کدی `:forms-v3`، replay ناسازگار v1.2 را جدا می‌کنند. دادهٔ نهایی قبلی حذف نمی‌شود.
