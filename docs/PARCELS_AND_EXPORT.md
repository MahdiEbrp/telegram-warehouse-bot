# چندمرسوله برای هر سفارش و خروجی Excel — v1.3.0

همهٔ این قابلیت‌ها **داخلی کارکنان** هستند. مشتری فعال، پنل عمومی، لینک عمومی استعلام یا اعلان خودکار ساخته نشده است. دانستن REF یا بارکد، دسترسی ایجاد نمی‌کند.

## چندمرسوله‌ای

مسیر: `/start` ← **سفارشات** ← سفارش ← **اطلاعات ارسال و رهگیری**. فهرست، شمارهٔ هر مرسوله و وضعیت آن را نشان می‌دهد؛ **افزودن مرسولهٔ جدید** و انتخاب هر رکورد جداست. در صفحهٔ مرسوله، کپی بارکد، لینک، ویرایش و ثبت ارسال/تحویل همان رکورد وجود دارد.

- هر مرسوله، شمارهٔ ترتیبی پایدار در همان سفارش، UUID، version، شرکت حمل، بارکد، لینک/کد پستی اختیاری، هزینه و یادداشت مستقل دارد.
- سقف **۲۰ مرسولهٔ جاری** برای هر سفارش است؛ عددِ شماره می‌تواند بیشتر از ۲۰ شود، چون پس از clear شماره تکرار نمی‌شود. سقف روی تعداد رکوردهای جاری است، نه بزرگ‌ترین شماره.
- شرکت حمل و ساختار کدها همان [TRACKING.md](TRACKING.md) است. بارکد برای پست/تیپاکس/چاپار/سایر لازم است؛ پیک/حضوری می‌توانند بدون آن باشند.
- ترکیب شرکت/نام سفارشی/بارکد باید یکتا باشد، حتی بین دو مرسولهٔ یک سفارش. بارکد متن است؛ صفر ابتدایی و بزرگی حروف حفظ می‌شوند.
- افزودن در `pending/confirmed/processing` مجاز است. پس از ارسال/تحویل کل سفارش، افزودن عادی بسته است؛ تنها تکمیل رکورد مفقودِ سفارش قدیمی با علت و مجوز لازم ممکن است.
- پاک‌کردن فقط **پیش‌نویس انتخاب‌شده**، با علت/تأیید و قبل از ارسال/لغو کل سفارش است. رکورد دیگر و REF/اقلام/موجودی تغییر نمی‌کنند؛ audit و شمارنده باقی می‌مانند.

### چرخهٔ مستقل و وضعیت کل سفارش

```text
draft (آماده‌سازی) → dispatched (ارسال‌شده) → delivered (تحویل‌شده)
```

ثبت مشخصات حمل به‌تنهایی نه وضعیت را جلو می‌برد و نه موجودی را تغییر می‌دهد. برای ارسال اولیهٔ پیش‌نویس، سفارش باید **processing + paid** باشد و اطلاعات حمل معتبر داشته باشد. حرکت وضعیت فقط رو به جلو است و timestamp آن زمان **ثبت دستی** است، نه استعلام شرکت حمل.

| نمونه                                                     | وضعیت کل سفارش          |
| --------------------------------------------------------- | ----------------------- |
| یکی ارسال و دیگری هنوز پیش‌نویس                           | processing باقی می‌ماند |
| همه ارسال‌شده یا تحویل‌شده، ولی حداقل یکی هنوز تحویل نشده | shipped                 |
| همه تحویل‌شده                                             | delivered               |

- پاک‌کردن آخرین پیش‌نویسِ ارسال‌نشده، وضعیت والد را بر اساس مرسوله‌های باقی‌مانده و در همان تراکنش با audit دوباره محاسبه می‌کند؛ موجودی تغییر نمی‌کند.
- پس از ارسال/تحویل حتی یک مرسوله، **لغو و برگشت موجودی ممنوع** است؛ processing ماندن والد نباید به لغو unsafe منجر شود.
- دکمهٔ وضعیت کل سفارش همچنان مسیر **جمعی** دارد. هشدار آن صریحاً می‌گوید همهٔ مرسوله‌های لازم جلو می‌روند؛ برای عمل روی یک بسته از صفحهٔ همان مرسوله استفاده کنید. اعتبارسنجی همهٔ رکوردها و تغییرات در یک تراکنش انجام می‌شود.
- اپراتور می‌تواند پیش از تحویل، اطلاعات را مدیریت کند. مرسولهٔ تحویل‌شده، **حتی اگر والد هنوز processing باشد**، فقط با مدیر/مدیرکل و علت اصلاح می‌شود. سفارش لغوشده برای همه خواندنی است.
- تأیید وضعیت/ویرایش به ID و version مشخص وابسته است؛ ویرایش هم‌زمان، دکمهٔ قدیمی را معتبر باقی نمی‌گذارد.
- برای legacy بدون زمان معلوم، timestamp جعلی ساخته نمی‌شود؛ والد shipped قدیمی بدون رکورد حمل، از ثبت تحویل محروم نمی‌شود.

**محدودیت مهم:** مرسوله‌ها فقط metadata ارسال هستند؛ تقسیم اقلام بین بسته‌ها، وزن/ابعاد، هزینهٔ مشتری، برگشت بسته، چاپ لیبل و API شرکت حمل پیاده‌سازی نشده‌اند. موجودی فقط در سفارش رزرو می‌شود، نه دوباره برای هر مرسوله.

## خروجی Excel بومی

مسیر: **سفارشات ← 📊 خروجی Excel مرسوله‌ها**؛ فقط **admin / super_admin**. اپراتور، viewer و مشتری نه دکمه دارند و نه با callback ساختگی به داده دسترسی می‌گیرند.

۱. صف سفارش را انتخاب کنید: همه، آماده‌سازی ارسال (`processing + paid`)، کل سفارش ارسال‌شده (`shipped`) یا قدیمی بدون اطلاعات حمل (`shipped/delivered` بدون مرسوله).
۲. وضعیت مرسوله را انتخاب کنید: همه / آماده‌سازی / ارسال‌شده / تحویل‌شده. برای قدیمی بدون اطلاعات، فقط «همه» کاربرد دارد.
۳. بازه: همهٔ تاریخ‌ها / امروز / ماه جاری **میلادی**.

**مبنای بازه، تاریخ ایجاد سفارش است؛ نه تاریخ ثبت ارسال یا تحویل.** مرزهای نیمه‌باز `[start,end)` با `STORE_TIMEZONE` محاسبه می‌شوند. خروجی زمان‌ها را UTC ISO نشان می‌دهد؛ sheet راهنما، بازه و timezone را ثبت می‌کند.

### ساختار و تفسیر فایل

- فایل واقعی `.xlsx` در حافظه ساخته و با `sendDocument` به همان گفت‌وگوی مجاز فرستاده می‌شود؛ CSV با پسوند عوض‌شده نیست.
- دو sheet: **مرسوله‌ها** و **راهنما**؛ راست‌به‌چپ، سطر عنوان ثابت و AutoFilter.
- **هر ردیف یک مرسوله** است. سفارشِ بدون مرسوله، در فیلتر «همه» یک ردیف با ستون‌های حمل خالی دارد؛ با فیلتر وضعیت مشخص، آن ردیف وارد خروجی نمی‌شود.
- ۲۱ ستون: REF، ORD، مشتری، تلفن، نشانی، کد پستی، وضعیت سفارش/پرداخت، شماره/وضعیت مرسوله، شرکت، بارکد، لینک، هزینهٔ داخلی، زمان ارسال/تحویل، یادداشت، زمان ایجاد سفارش/مرسوله، ویرایش و نسخه.
- کد/تلفن/کد پستی **متنی** هستند؛ صفر و case از بین نمی‌روند. هزینه، شماره و نسخه عددی‌اند. زمان نامعلوم خالی است، نه مقدار حدسی.
- مبلغ کل سفارش تکرار نمی‌شود تا جمع‌زدن چند ردیف، فروش را چندبار حساب نکند. هزینهٔ حمل داخلی است؛ جمع آن، فروش/وجه مشتری/سود خالص نیست.
- رشته‌های شروع‌شونده با `=`, `+`, `-`, `@` همچنان literal هستند؛ فرمول، macro، hyperlink فعال یا relationship خارجی ساخته نمی‌شود. XML escape و نویسه‌های نامعتبر sanitize می‌شوند؛ متن حملِ دارای کنترل نامعتبر قبل از ذخیره رد می‌شود.

### سقف و محرمانگی

- سقف هر فایل **۱۰۰۰ ردیف** و ۸ MiB است. query حداکثر ۱۰۰۱ ردیف می‌خواند و در صورت عبور از سقف **خطا می‌دهد؛ فایل ناقص یا بی‌صدا بریده تحویل نمی‌دهد**. از بازه/فیلتر کوچک‌تر استفاده کنید؛ خروجی تاریخ دلخواه/pagination/آرشیو حجیم در این انتشار نیست.
- نام فایل، تعداد ردیف/سفارش و SHA-256 در پیام همراه است. hash برای تطبیق فایل است، نه امضای دیجیتال ضد‌دستکاری.
- audit با نام `shipment.export.generated` فقط فیلتر، تعدادها، حجم و hash را نگه می‌دارد؛ محتوای فایل یا PII مشتری در این audit کپی نمی‌شود. audit ارسال‌های دیگر ممکن است metadata حساس داشته باشد.
- «generated» **اثبات تحویل به Telegram نیست**؛ ارسال ممکن است بعد از ثبت audit شکست بخورد. تضمین exactly-once پیام/فایل خروجی نداریم.
- فایل روی دیسک عمومی، object storage یا لینک دانلود عمومی ذخیره نمی‌شود. با این حال فایل Telegram ممکن است ذخیره/فوروارد شود؛ کارکنان باید سیاست دسترسی، retention و عدم انتشار اطلاعات مشتری را رعایت کنند. خروجی گروهی PII عمداً در اختیار اپراتور نیست.

## نمونه و تست

`docs/samples/shipments-demo.xlsx` نمونهٔ **صرفاً ساختگی** با دو مرسوله و یک سفارش بدون مرسوله است. با `openpyxl 3.1.5` مستقل از نویسندهٔ JS باز و بررسی شده است؛ به Telegram واقعی ارسال نشده است.

تست‌ها، سقف/نوع داده/فرمول literal، فیلترها، دسترسی، rollback و revision، گردش چندمرسوله و ارسال `InputFile` از pipeline واقعی TestBot را می‌سنجند. شواهد: [TESTING.md](TESTING.md) و [VERIFICATION.md](VERIFICATION.md). ارتقای امن: [UPGRADE.md](UPGRADE.md).
