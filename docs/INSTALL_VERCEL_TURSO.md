# نصب تازه روی Vercel + Turso — نسخهٔ 1.3.0

این مسیر برای **نصب تازه، بدون دیتابیس عملیاتی قبلی** است؛ همان گزینهٔ انتخاب‌شده برای این تحویل. اگر دادهٔ قبلی دارید، ابتدا [UPGRADE.md](UPGRADE.md) را بخوانید.

**وضعیت تحویل:** سورس، migration، تست‌ها و تنظیمات آماده‌اند؛ در این محیط هیچ پروژهٔ Vercel، دیتابیس ابری یا Webhook واقعی برای شما ایجاد نشده است. کلیدها را در چت، سورس، اسکرین‌شات یا Git قرار ندهید. اتصال حساب Vercel و تنظیم خصوصی اطلاعات Turso برای انتشار واقعی لازم‌اند.

## ۱. آماده‌سازی فایل‌ها

ZIP را استخراج کنید و وارد پوشهٔ `telegram-warehouse-bot` شوید. Node.js **24.x** نصب باشد:

```bash
node --version
npm ci
cp .env.example .env
```

فایل `.env` فقط برای ابزارهای محلیِ امن است؛ به Vercel یا Git آپلودش نکنید. در Vercel، متغیرها را جداگانه در تنظیمات Environment Variables وارد کنید. این پروژه وب‌پنل ندارد؛ Route اصلی فقط JSON برمی‌گرداند.

## ۲. بات و مدیرکل

- از BotFather توکن بات خودتان را بگیرید و خصوصی در `BOT_TOKEN` ذخیره کنید.
- شناسهٔ **عددی** حساب شخصی مدیرکل را در `SUPER_ADMIN_TELEGRAM_IDS` قرار دهید؛ username یا شماره تلفن جایگزین آن نیست.
- قبل از اولین `/start` مدیر، این متغیر باید در Production تنظیم شده باشد. کاربر تازه bootstrap می‌شود؛ حساب از قبل موجود خودکار ارتقا نمی‌یابد.
- secret تصادفی جدید بسازید و خصوصی در `TELEGRAM_WEBHOOK_SECRET` بگذارید:

```bash
openssl rand -hex 32
```

این secret باید بین تنظیمات اجرای بات و script ثبت Webhook یکسان باشد. آن را در URL قرار ندهید.

## ۳. دیتابیس Turso سازگار با libSQL

این کد از **`@libsql/client` + Drizzle libSQL** استفاده می‌کند. در مستندات فعلی Turso دو engine معرفی شده‌اند؛ برای این پروژه **libSQL** بسازید، نه engine جدید با فلگ `--tursodb`. دستور بدون این فلگ، libSQL می‌سازد. [1](https://docs.turso.tech/quickstart)

پس از نصب CLI رسمی و ورود به حساب خودتان، نمونهٔ زیر را با نام انتخابی خود اجرا کنید؛ نام ممکن است در حساب شما قبلاً استفاده شده باشد:

```bash
turso auth login
turso db create warehouse-bot
turso db show warehouse-bot --url
turso db tokens create warehouse-bot
```

دستور `db show ... --url`، URL اتصال را نشان می‌دهد. خروجی آن را در `TURSO_DATABASE_URL` قرار دهید. [5](https://docs.turso.tech/cli/db/show)

توکن تولیدشدهٔ تک‌دیتابیس را خصوصی در `TURSO_AUTH_TOKEN` بگذارید؛ اپلیکیشن سفارش و موجودی می‌نویسد، پس توکن read-only کافی نیست. انقضا و تمدید توکن را مطابق سیاست خود تنظیم کنید. [2](https://docs.turso.tech/cli/db/tokens/create)

برای این بسته، URL باید `libsql://...` یا HTTPS سازگار با libSQL باشد؛ `turso://...` و SDK موتور جدید در این انتشار پیاده‌سازی نشده‌اند. یک دیتابیس مستقل برای هر بات/محیط انتخاب کنید. مکان دیتابیس و Vercel را تا حد امکان نزدیک و طبق الزامات نگهداری دادهٔ خود انتخاب کنید؛ ظرفیت واقعی به سرویس و سهمیهٔ حساب شما وابسته است.

## ۴. مقداردهی env و ایجاد schema

در `.env` امن محلی و بعداً در Vercel، این متغیرها را با **مقادیر واقعی خودتان** تنظیم کنید:

| متغیر                      | مقدار/نکته                                                      |
| -------------------------- | --------------------------------------------------------------- |
| `BOT_TOKEN`                | محرمانه؛ از BotFather                                           |
| `TELEGRAM_WEBHOOK_SECRET`  | محرمانه؛ secret تصادفی مرحلهٔ ۲                                 |
| `SUPER_ADMIN_TELEGRAM_IDS` | شناسهٔ عددی مدیرکل؛ چند شناسه با کاما                           |
| `TURSO_DATABASE_URL`       | دیتابیس libSQL همان محیط Production؛ نه `file:`                 |
| `TURSO_AUTH_TOKEN`         | محرمانه؛ توکن همان دیتابیس با اجازهٔ نوشتن                      |
| `APP_URL`                  | origin عمومی HTTPS نهایی Vercel؛ بدون `/api/...`، query یا hash |
| `STORE_TIMEZONE`           | `Asia/Tehran` یا IANA zone معتبر خودتان                         |
| `CONVERSATION_VERSION`     | `4`                                                             |
| `WEBHOOK_MAX_CONNECTIONS`  | برای شروع `1`؛ تضمین FIFO نیست                                  |

با URL و توکن **همین دیتابیس تازهٔ ابری** اجرا کنید:

```bash
npm run db:migrate
npm run db:seed
```

این دو فرمان به Telegram وصل نمی‌شوند. migrationهای `0000`، `0001` و `0002` اجرا می‌شوند و **۱۵ جدول کاربردی** می‌سازند؛ جدول journal داخلی Drizzle جداست. seed فقط دستهٔ عمومی/تنظیمات اولیه را درج می‌کند؛ محصول، سفارش، حساب مشتری یا پرداخت واقعی نمی‌سازد.

migration/seed را در build، Route یا Cron عمومی قرار ندهید. برای نصب تازه معمولاً `admin:bootstrap` لازم نیست؛ فقط برای بازیابی آگاهانهٔ حساب موجود و با تأیید صریح است.

## ۵. استقرار Vercel

کد را در پروژهٔ خودتان وارد کنید؛ می‌توانید از مخزن خصوصی خودتان یا CLI واردشده به حساب خودتان استفاده کنید:

```bash
npx vercel
# پس از بررسی تنظیمات و envهای Production:
npx vercel --prod
```

- Root Directory همان پوشه‌ای باشد که `package.json` دارد.
- Framework: Next.js؛ Node: **24.x**؛ install: `npm ci`؛ build: `npm run build`. فایل `vercel.json` این فرمان‌ها را دارد.
- envها را در scope صحیح **Production** تنظیم کنید. نام secretها نباید با `NEXT_PUBLIC_` شروع شود.
- SQLite فایل محلی در Vercel عمداً رد می‌شود؛ filesystem تابع، storage پایدار این بات نیست.
- دامنهٔ Production و مسیر Webhook باید برای Telegram بدون ورود به حساب Vercel در دسترس باشند. Protection را فقط برای دامنه/محیط لازم تنظیم کنید؛ secret هدر Webhook همچنان الزامی است.
- محیط Preview را به همان بات/دیتابیس Production وصل نکنید. یک بات فقط یک Webhook فعال دارد.

پس از deploy، `GET /api/health` باید 200 بدهد؛ این فقط **liveness** است، نه تست اتصال Turso یا Telegram.

## ۶. بررسی فقط‌خواندنی پیش از ثبت Webhook

`APP_URL` را با دامنهٔ Production نهایی در هر دو محیط هماهنگ و از دستگاه امن اجرا کنید:

```bash
npm run deploy:check
```

این ابزار env تولیدی، URL عمومی، نبود placeholder، ستون‌های v1.2، شمارنده‌ها، نبود ایندکس تک‌مرسوله‌ای قدیمی، فعال‌بودن/سلامت FK و REFهای مفقود را بررسی می‌کند. سفارش، کاربر یا audit ایجاد نمی‌کند؛ migration، استقرار و ثبت Webhook هم انجام نمی‌دهد. **توکن Telegram، اجازهٔ نوشتن عملیاتی، دسترس‌پذیری دامنهٔ Vercel، ظرفیت یا تحویل پیام را تأیید نمی‌کند.**

اگر URL محلی، env ناقص یا schema قدیمی باشد، با exit code ناموفق متوقف می‌شود. برای دورزدن آن، داده یا migration journal را پاک نکنید؛ پیکربندی/ارتقا را اصلاح کنید.

## ۷. ثبت Webhook و پذیرش واقعی

با env همان بات و secret یکسان:

```bash
npm run webhook:set
npm run webhook:info
```

script، مسیر `/api/telegram/webhook`، فقط updateهای `message/callback_query` و فقط دستور `/start` را ثبت می‌کند؛ pending updates دور ریخته نمی‌شوند.

چک‌لیست در محیط تست واقعیِ جدا از دادهٔ عملیاتی:

- [ ] مدیر در گفت‌وگوی خصوصی `/start` می‌فرستد و داشبورد را می‌بیند.
- [ ] محصول نمونه و سفارش چندقلمی ایجاد و موجودی کنترل می‌شود.
- [ ] پرداخت دستی تأیید و سفارش به پردازش می‌رود.
- [ ] از صفحهٔ رهگیری، دو مرسوله با کدهای جدا ساخته می‌شوند.
- [ ] ارسال مرسولهٔ اول، وضعیت کل سفارش را زودتر از موعد «ارسال‌شده» نمی‌کند.
- [ ] ارسال/تحویل همهٔ مرسوله‌ها، وضعیت نهایی کل سفارش را درست می‌کند.
- [ ] مدیر/مدیرکل از فهرست سفارشات فایل Excel را دریافت و صفرهای ابتدایی کدها را بررسی می‌کند.
- [ ] اپراتور/بیننده به خروجی Excel دسترسی ندارد؛ مشتری پیام، اعلان یا پنل رهگیری دریافت نمی‌کند.
- [ ] `webhook:info` خطای فعال ثبت نمی‌کند و خطاها بدون افشای کلید پایش می‌شوند.

این چک‌لیست با حساب واقعی شما **هنوز اجرا نشده است**. تست‌های TestBot و SQLite داخل بسته، جای این مرحله را نمی‌گیرند.
