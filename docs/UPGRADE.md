# ارتقا و برگشت امن — نسخهٔ 1.3.0

برای **نصب تازهٔ انتخاب‌شده در این تحویل**، مسیر اصلی [INSTALL_VERCEL_TURSO.md](INSTALL_VERCEL_TURSO.md) است. این راهنما برای کسانی است که بستهٔ v1.0/v1.1/v1.2 را قبلاً اجرا کرده‌اند؛ هیچ دیتابیس واقعی شما در این محیط تغییر نکرده است.

## از v1.2 به v1.3 — بدون تغییر schema

۱. از DB و env صحیح backup قابل بازیابی بگیرید، writer قدیمی را متوقف کنید و Node 24 / `npm ci` را آماده کنید.
۲. `CONVERSATION_VERSION=4` را تنظیم کنید. namespace کدی `:forms-v3` حتی با env قدیمی، replay فرم قبلی را جدا می‌کند؛ فرم‌های نیمه‌تمام از نو آغاز می‌شوند، نه سفارش‌های ثبت‌شده.
۳. `npm run db:migrate` همچنان امن و idempotent است ولی **هیچ 0003 یا تغییر جدول تازه‌ای در v1.3 نیست**. `db:seed` برای ارتقا لازم نیست.
۴. typecheck، coverage، stress آفلاین و build را اجرا کنید، سپس محیط صحیح را deploy و Webhook را دوباره بررسی کنید. آزمون محلی جای staging تلگرام/Turso نیست.
۵. داده‌های قدیمی بازنویسی جمعی نمی‌شوند؛ اعتبارسنجی متن/URL هنگام ویرایش سخت‌گیرانه‌تر شده است. URL تصویر با نام کاربری/رمز/پورت سفارشی، IP صریح یا Unicode خراب باید اصلاح یا پاک شود.

برگشت **فقط از v1.3 به v1.2** به دلیل schema یکسان معمولاً به restore نیاز ندارد، ولی writerها را متوقف و conversationها را نامعتبر کنید و ابتدا در محیط جدا بسنجید. restore بی‌برنامه می‌تواند سفارش‌های جدید را از بین ببرد. هشدارهای زیر برای برگشت به **v1.1/v1.0** همچنان برقرارند.

## ارتقای v1.0/v1.1 به schema چندمرسوله‌ای

## تغییرات schema

| مایگریشن            | اثر                                                                   |
| ------------------- | --------------------------------------------------------------------- |
| `0000_initial.sql`  | schema اولیه؛ بدون تغییر نسبت به تحویل قبلی                           |
| `0001_tracking.sql` | REF و اطلاعات ارسال v1.1؛ بدون تغییر نسبت به تحویل قبلی               |
| `0002_parcels.sql`  | افزودن شماره/وضعیت مرسوله و جدول شمارنده؛ تبدیل رابطه به چندمرسوله‌ای |

`0002`، SQL آمادهٔ بازبینی‌شده است؛ `shipments` یا `orders` را بازسازی/حذف نمی‌کند و در SQL آن خاموش‌کردن FK وجود ندارد. شمارهٔ مرسولهٔ قبلی ۱ می‌شود؛ وضعیت از timestamp موجود یا وضعیت والد استنباط می‌شود. زمان تاریخی نامعلوم، «الان» فرض نمی‌شود. ID، تمام ستون‌های قدیمی، بارکد، نسخه، سازنده/ویرایشگر، تاریخ‌ها و auditها حفظ می‌شوند. ایندکس یکتای قدیمی `order_id` جای خود را به `(order_id, parcel_number)` می‌دهد؛ یکتایی بارکد شرکت حمل حفظ می‌شود.

از v1.0، migrator هر دو ارتقای 0001 و 0002 را به ترتیب اجرا می‌کند. از v1.1 فقط 0002 جدید اجرا می‌شود. شمارنده برای مرسوله‌های موجود مقدار می‌گیرد و بعد از پاک‌کردن پیش‌نویس نیز شمارهٔ قبلی را تکرار نمی‌کند.

## مراحل پیش از نوشتن دادهٔ جدید

1. **ورودی و نویسندگان قدیمی را متوقف کنید.** با env همان بات:

   ```bash
   npm run webhook:delete
   ```

   script از `drop_pending_updates: false` استفاده می‌کند. صبر کنید workerهای درحال‌اجرا تمام شوند؛ حذف Webhook به‌تنهایی worker فعال یا jobهای دیگر را متوقف نمی‌کند. در self-host، فرایند قبلی را متوقف کنید. عملیات migration روی DB مشترک بدون توقف نویسندگان قدیمی، مسیر پشتیبانی‌شدهٔ این بسته نیست.

2. **backup سازگار و قابل بازیابی بگیرید.** برای SQLite، ابزار backup خود SQLite را به‌جای کپی خام فایل فعالِ WAL به‌کار ببرید، مثلاً با مسیر واقعی خودتان:

   ```bash
   sqlite3 data/warehouse.db ".backup 'data/warehouse-before-v1.2.db'"
   ```

   برای Turso، snapshot/backup و روش restore متناسب با حساب و سرویس خودتان را آماده کنید. backup به‌تنهایی کافی نیست؛ مسیر بازگرداندن را در محیط جدا بررسی کنید. از حساب ابری شما در این تحویل backup گرفته نشده است.

3. **کد، env و DB صحیح را منطبق کنید.** Node 24 و بستهٔ جدید را آماده کنید. `.env` و داده‌ها را حذف نکنید. اگر به پوشهٔ تازه می‌روید، URL نسبی `file:` را به همان DB پایدار اصلاح کنید؛ مایگریشن تصادفی روی DB خالی، ارتقای دیتابیس قبلی نیست. کلیدها را در مخزن/چت قرار ندهید.

4. **ارتقا و کنترل کیفیت** را از پوشهٔ پروژه اجرا کنید:

   ```bash
   npm ci
   # در env اجرای نسخهٔ جدید: CONVERSATION_VERSION=4
   npm run db:migrate
   npm run typecheck
   npm test
   npm run build
   # فقط برای پیکربندی Production ابری با APP_URL درست:
   npm run deploy:check
   ```

   `db:seed` برای این ارتقا لازم نیست. `db:generate` یا `drizzle-kit push` جایگزین migrationهای آماده نیستند. journal را دستی پاک نکنید تا migration دوباره اعمال شود.

5. **انتشار و بررسی**: کد جدید را با env صحیح اجرا/deploy کنید؛ سلامت اتصال و یک سفارش قبلی، بارکد، audit و شمارهٔ مرسوله را بررسی کنید. سپس:

   ```bash
   npm run webhook:set
   npm run webhook:info
   ```

   ویزاردهای نیمه‌تمام نسخهٔ قبل عمداً کنار گذاشته می‌شوند. namespace کدی `:forms-v3` جلوی replay ناسازگار را حتی با env قدیمی می‌گیرد؛ مقدار پیشنهادی env اکنون `4` است. رکوردهای سفارش و دادهٔ نهایی حذف نمی‌شوند.

## تغییرات رفتاری مهم برای کد داخلی شما

- `orders.get(...).shipments` آرایهٔ مرتب همهٔ مرسوله‌هاست. فیلد سازگاری `.shipment` فقط وقتی دقیقاً یک مرسوله وجود دارد پر می‌شود.
- `shipments.get(actor, orderId)` روی چند مرسوله خطای `SHIPMENT_AMBIGUOUS` می‌دهد؛ از `list/getById` یا شناسهٔ مشخص استفاده کنید. هیچ «اولین مرسولهٔ حدسی» انتخاب نمی‌شود.
- `save(..., expected=null, ...)` یعنی **ایجاد مرسولهٔ جدید**؛ برای ویرایش، ID و version دقیق لازم است. کد سفارشی قدیمی را با این قرارداد هماهنگ کنید.
- callbackهای قدیمیِ تک‌مرسوله‌ای روی سفارش چندمرسوله‌ای به انتخاب مرسوله هدایت می‌شوند. تأیید کهنهٔ وضعیت، revision جدید را دور نمی‌زند.
- لغو/برگشت موجودی پس از ارسال حتی **یکی** از مرسوله‌ها ممنوع است؛ والدِ هنوز processing مجوز لغو خطرناک ایجاد نمی‌کند.
- شمارهٔ مرسوله، تخصیص کالا نیست؛ اقلام/موجودی دوباره رزرو نمی‌شوند.

## rollback

- **پیش از فعال‌کردن نوشتن**، برگشت به کد قبلی و **backup منطبق قبلی** ممکن است؛ همهٔ writerها را متوقف نگه دارید و restore را با طرح خودتان انجام دهید.
- **پس از نوشتن v1.2**، restore می‌تواند سفارش و تغییرات جدید را از بین ببرد. رفع رو به جلو را ترجیح دهید؛ backup را بدون برنامهٔ تطبیق داده برنگردانید.
- فقط تعویض کد به v1.1 امن نیست: schema اکنون چندمرسوله‌ای است، اما کد قبلی فرض یک رکورد/سفارش دارد. فقط برگشت کد v1.0 هم می‌تواند سفارش‌های بدون REF بسازد؛ migrator اعمال‌شده آن‌ها را خودکار دوباره backfill نمی‌کند.
- حذف مرسوله‌های اضافه، حذف ستون‌ها، پاک‌کردن audit یا reset journal راه rollback نیست. down migration مخرب تحویل داده نشده است.
- در صورت شکست migration یا ابهام سازگاری، writerها را خاموش نگه دارید؛ خطا را با backup بررسی کنید، نه با اجرای تصادفی `push/seed/bootstrap`.

## شواهد قابل بازتولید

`integration/upgrade.test.ts`، ارتقای v1.0 پرشده و حفظ ۱۲ جدول قبلی را می‌سنجد. `integration/parcels-upgrade.test.ts`، schema واقعی v1.1 با **۱۴ جدول**، مرسوله‌های تاریخی/زمان نامعلوم/نسخهٔ ۴۲/actor/audit را به **۱۵ جدول** ارتقا می‌دهد و تمام ستون‌های قبلی را مقایسه می‌کند. تکرار migration، FK و عدم استفادهٔ دوباره از شماره پس از clear نیز تست شده‌اند.

این شواهد مربوط به SQLite آزمایشی‌اند، نه اجرای migration روی Turso یا دادهٔ واقعی شما. نتایج کامل: [VERIFICATION.md](VERIFICATION.md).
