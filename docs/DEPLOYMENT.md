# راهنمای استقرار و عملیات — v1.3.0

برای نصب تازهٔ انتخاب‌شده، [INSTALL_VERCEL_TURSO.md](INSTALL_VERCEL_TURSO.md) مسیر اصلی است. این صفحه مرجع عملیات است؛ حساب واقعی شما در این محیط متصل/منتشر نشده است.

## متغیرهای محیطی

| نام                        | کاربرد                                                                      |
| -------------------------- | --------------------------------------------------------------------------- |
| `BOT_TOKEN`                | توکن واقعی از BotFather؛ هرگز `NEXT_PUBLIC_` نباشد                          |
| `TELEGRAM_WEBHOOK_SECRET`  | ۳۲ تا ۲۵۶ نویسه از `A-Z a-z 0-9 _ -`؛ همان secret ثبت Webhook               |
| `SUPER_ADMIN_TELEGRAM_IDS` | شناسه‌های عددی جداشده با کاما؛ فقط bootstrap کاربر تازه                     |
| `TURSO_DATABASE_URL`       | `file:` برای توسعه یا `libsql://`/`https://` برای اتصال ابری                |
| `TURSO_AUTH_TOKEN`         | برای دیتابیس ابری الزامی است                                                |
| `APP_URL`                  | دامنهٔ عمومی HTTPS برای فرمان ثبت Webhook؛ Route را خود script اضافه می‌کند |
| `STORE_TIMEZONE`           | پیش‌فرض `Asia/Tehran`؛ منطقهٔ معتبر IANA برای گزارش‌ها                      |
| `CONVERSATION_VERSION`     | پیش‌فرض `4`؛ با تغییر ناسازگار مراحل ویزارد افزایش دهید                     |
| `WEBHOOK_MAX_CONNECTIONS`  | پیش‌فرض محافظه‌کارانهٔ `1`؛ فقط در فرمان setWebhook مصرف می‌شود             |

نام متغیر URL همان نام درخواستی `TURSO_DATABASE_URL` است؛ حتی در توسعه برای SQLite. فایل `.env` را هم Next و هم scriptها می‌خوانند. اگر از `.env.local` استفاده می‌کنید، برای scriptها نیز env را به shell تزریق کنید؛ راه پیشنهادی همین `.env` است.

## ارتقای نسخهٔ قبلی

v1.3 نسبت به v1.2 migration تازه ندارد؛ `0002_parcels.sql` همراه migrationهای قبلیِ بدون تغییر حفظ شده است؛ نصب تازه ۱۵ جدول کاربردی دارد. از v1.0/v1.1، writer قدیمی را متوقف و backup منطبق بگیرید و migration آماده را روی **همان دیتابیس صحیح** اجرا کنید. `CONVERSATION_VERSION=4` توصیه می‌شود. فقط برگرداندن کد قدیمی پس از چندمرسوله‌ای شدن schema، rollback امن نیست. راهنمای توقف، backup و بازیابی: [UPGRADE.md](UPGRADE.md).

## Vercel

1. Node 24.x، framework برابر Next.js، install برابر `npm ci` و build برابر `npm run build`.
2. تمام envهای Production را تنظیم کنید. مسیر Webhook Node runtime دارد، نه Edge؛ استفاده از libSQL محلی/native با Edge در این پروژه پشتیبانی نشده است.
3. در محیط امن، URL و توکن **همان دیتابیس Production سازگار با libSQL** را export و مایگریشن را جداگانه اجرا کنید:

```bash
export TURSO_DATABASE_URL='libsql://YOUR-DATABASE.turso.io'
export TURSO_AUTH_TOKEN='YOUR-DATABASE-TOKEN'
npm run db:migrate
npm run db:seed
```

مایگریشن/seed به Bot API وصل نمی‌شوند و به توکن بات نیاز ندارند. قبل از migration روی دادهٔ واقعی، backup بگیرید. `db:generate` کار توسعه است؛ SQL ایجادشده را بازبینی و commit کنید. `drizzle-kit push` در مسیر استقرار پیشنهاد نشده است.

4. deploy کنید؛ `/api/health` باید 200 بدهد. این مسیر readiness دیتابیس نیست. پس از تنظیم `APP_URL` نهایی، `npm run deploy:check` را از دستگاه امن اجرا کنید؛ فقط env و schema/سلامت داده را می‌سنجد، نه Telegram، امکان نوشتن واقعی، دسترسی عمومی دامنه یا deployment. `vercel.json` همراه پروژه است.
5. آدرس Production باید برای Telegram عمومی باشد. اگر Deployment Protection آن را به صفحهٔ ورود می‌برد، فقط دامنهٔ مناسب Production را عمومی کنید؛ secret خود Webhook همچنان الزامی است. محیط Preview را از Production جدا و برای تست از بات و دیتابیس جدا استفاده کنید.
6. از دستگاه امن با envهای همان بات:

```bash
export APP_URL='https://YOUR-APP.vercel.app'
npm run webhook:set
npm run webhook:info
```

script از `setWebhook` با این گزینه‌ها استفاده می‌کند:

```ts
{
  secret_token: env.TELEGRAM_WEBHOOK_SECRET,
  allowed_updates: ["message", "callback_query"],
  max_connections: env.WEBHOOK_MAX_CONNECTIONS,
  drop_pending_updates: false
}
```

فقط `/start` نیز با `setMyCommands` ثبت می‌شود. حذف Webhook، آپدیت‌های معلق را دور نمی‌ریزد:

```bash
npm run webhook:delete
```

7. در گفت‌وگوی خصوصی `/start` بفرستید؛ سپس ایجاد محصول و یک سفارش آزمایشی را در محیط staging واقعی بررسی کنید. بدون کلیدهای واقعی، این مرحله در تحویل انجام نشده است.

## مقیاس‌پذیری و هم‌زمانی

- **SQLite محلی فقط یک فرایند Node:** هر client محلی یک connection دارد تا FK/timeout روی همهٔ عملیات فعال بمانند؛ تمام read/writeهای مستقل و کل عمر تراکنش، بین clientهای همان فایل در همان فرایند صف می‌شوند. این کار هم از connection تازهٔ بدون PRAGMA و هم از مسیر خطای native BUSY جلوگیری می‌کند؛ به سرویس‌های دامنه، lease و idempotency دست نمی‌زند.
- این صف **نه قفل بین‌فرایندی است نه راهکار Vercel**. هم‌زمان چند process/job روی یک فایل محلی اجرا نکنید؛ برای چند نمونهٔ سرور و Production از Turso مشترک استفاده کنید. در اتصال remote این صف محلی اعمال نمی‌شود. هیچ تراکنشی را با I/O شبکه یا خواندن از client بیرونی در callback تراکنش باز نگه ندارید؛ داخل callback فقط `tx` را به‌کار ببرید.

- سرورها stateless هستند: دیتابیس مشترک، source of truth برای ویزارد، receipt و مجوزهاست. حافظهٔ محلی، جای storage مشترک را نمی‌گیرد.
- قفل ۱۲۰ ثانیه‌ای برای ترکیب کاربر/چت، دو اجرای هم‌زمان یک ویزارد را رد می‌کند. قفل اشغال‌شده 503 می‌دهد؛ مدعی FIFO یا ترتیب کامل همهٔ Webhookهای Telegram نیستیم.
- نوشتن دامنه و storage، مالکیت قفل را در تراکنش دوباره می‌سنجند تا worker قدیمی state جدید را بازنویسی نکند.
- `maxDuration=60` برای Vercel و timeout پاسخ Webhook برابر ۵۵ ثانیه است. کد بعد از ACK در پس‌زمینه رها نمی‌شود و `onTimeout: "return"` استفاده نشده است. در self-host نیز timeout سخت worker کمتر از زمان lease بگذارید.
- API timeout بات ۱۰ ثانیه است. موفقیت Webhook بعد از پایان middleware و ذخیرهٔ state پاسخ داده می‌شود؛ webhook reply زودهنگام غیرفعال است.
- مقدار پیش‌فرض `max_connections=1` برای شروع محافظه‌کارانه است. افزایش آن امکان پردازش چت‌های مستقل را می‌دهد، ولی تضمین ترتیب/صف منصفانه ایجاد نمی‌کند؛ قبل از افزایش، بار و retryهای هم‌چت را آزمایش کنید. برای حجم زیاد، صف پایدار partitionشده بر اساس chat/user، worker و outbox اضافه کنید.
- گزارش بار آفلاین در [STRESS_TEST.md](STRESS_TEST.md) وجود دارد؛ benchmark ظرفیت ابری/تلگرام یا ادعای مقیاس نامحدود نیست. سقف write/transaction در Turso، منطقهٔ استقرار و سهمیهٔ Telegram باید پایش شوند.

## نگهداری

```bash
npm run db:cleanup
```

این فرمان conversationها و lockهای منقضی و receiptهای قدیمی‌تر از ۳۰ روز را پاک می‌کند؛ کلیدهای عملیات کسب‌وکار و audit را حذف نمی‌کند. برای Turso آن را روزانه در job امن خارجی اجرا کنید؛ در توسعهٔ فایل محلی، نویسندهٔ دیگر را هم‌زمان فعال نگذارید. هیچ endpoint عمومی cleanup/seed/migration ساخته نشده است. صرفاً گذشت TTL، حذف فیزیکی داده نیست؛ job cleanup لازم است.

اطلاعات مشتری در order باقی می‌ماند؛ خروجی Excel نیز شامل آن است، فقط برای مدیر/مدیرکل و بدون لینک عمومی. audit تولید فایل، تضمین تحویل نیست. [قواعد خروجی](PARCELS_AND_EXPORT.md). برای retention، export، حذف/ناشناس‌سازی قانونی و backup سیاست مستقل تعریف کنید. دیتابیس هر بات و هر محیط را جدا کنید.

## عیب‌یابی

- **401:** secret موجود در Vercel با `setWebhook` یکی نیست؛ پس از اصلاح، دوباره ثبت کنید.
- **503:** اختلال موقت دیتابیس/تلگرام یا قفل همان چت؛ Telegram باید retry کند. خطاهای سرور را بدون چاپ توکن بررسی کنید.
- **حساب غیرفعال:** مدیرکل باید دسترسی را از UI فعال کند. تغییر env، حساب موجود را خودکار ارتقا نمی‌دهد؛ فقط در بازیابی آگاهانه از `admin:bootstrap -- --confirm` استفاده کنید.
- **ویژگی disabled کار نمی‌کند:** از Bot API 10.3 یا جدیدتر و نسخه‌های قفل‌شدهٔ پکیج‌ها استفاده کنید. دکمهٔ disabled، `callback_data` ندارد؛ `disabled: true` نفرستید.
- **انبار قدیمی/موجودی تغییرکرده:** محصول را دوباره باز کنید. این تعارض عمدی است، نه خطای محاسبه.
- **فروش ماهانه با ماه شمسی متفاوت است:** بازهٔ گزارش در این نسخه میلادی است؛ عنوان این موضوع را مشخص می‌کند.
- **ارسال جدید مسدود است:** سفارش باید processing و پرداخت آن paid باشد؛ سپس شرکت حمل و بارکد را در اطلاعات ارسال ثبت کنید (پیک/حضوری بدون بارکد مجاز است). سفارش قدیمیِ از قبل shipped همچنان قابل ثبت تحویل است.
- **اطلاعات ارسال هم‌زمان تغییر کرده:** صفحه را دوباره باز کنید؛ revision قدیمی عمداً بازنویسی نمی‌کند.
- **خروجی Excel بیش از سقف:** بازه/فیلتر را محدود کنید؛ بیش از ۱۰۰۰ ردیف عمداً بریده تحویل نمی‌شود. تاریخ فیلتر، ایجاد سفارش است، نه زمان ارسال.
- **چندمرسوله و لغو:** حتی با والد processing، پس از ارسال یک مرسوله لغو/برگشت موجودی بسته است. وضعیت هر بسته را در صفحهٔ خودش مدیریت کنید.
- **شروع محلی با polling:** در این پروژه polling اجرا نمی‌شود؛ Next را بالا بیاورید، تونل HTTPS بگیرید و Webhook را ثبت کنید. یک بات نمی‌تواند هم‌زمان Webhook فعال و long polling داشته باشد.
