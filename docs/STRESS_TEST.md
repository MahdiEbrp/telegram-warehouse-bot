# تست فشار قابل بازتولید — v1.3.0

## هدف انتخاب‌شده

**۵۰ کاربر مجازی هم‌زمان / ۵۰۰۰ آپدیت مصنوعی آفلاین**. نتیجهٔ اجرای تحویل: **PASS؛ هر ۲۰ invariant موفق**. این یک آزمون کامل pipeline بات با DB و validation واقعی است، اما **benchmark HTTP/Telegram/Vercel/Turso ابری نیست** و امتیاز یا تضمین «۱۰/۱۰» صادر نمی‌کند.

گزارش خام: [stress-50x5000.json](verification/stress-50x5000.json). شروع `2026-10-25T08:00:55.333Z`؛ پایان `2026-10-25T08:01:11.785Z`. Node `v24.22.1`، Linux x64؛ parallelism اعلام‌شدهٔ میزبان `2`.

## اجرای دوباره

بدون secret یا حساب ابری، با Node 24:

```bash
npm ci
npm run test:stress
# دقیقاً همین هدف و مسیر خروجی دلخواه:
npm run test:stress -- --users 50 --updates 5000 --output docs/verification/stress-50x5000.json
# اجرای کوتاه برای توسعه:
npm run test:stress:smoke
```

CLI گزارش موفق قبلیِ همان مسیر را **پیش از تلاش تازه پاک می‌کند**؛ در شکست، فایل قدیمی شاهد موفقیت جا نمی‌ماند. شکست invariant یا خطای runner، exit code غیرصفر دارد. زمان/latency هر اجرا با منابع میزبان تغییر می‌کند؛ اعداد زیر SLA نیستند.

## روش و workload

- همان `configureBot`، middlewareهای auth/RBAC/reliability، conversations و سرویس‌های تراکنشی اجرا می‌شوند؛ نه تابع mock برای عملیات کسب‌وکار.
- `@bonkers-agency/grammy-test`، Telegram را شبیه‌سازی می‌کند. fetch واقعی guard دارد؛ پاسخ‌ها با AsyncLocalStorage بین کاربران جدا می‌شوند. callback از پیام و token واقعی همان پنل انتخاب می‌شود.
- DB برابر `file::memory:` با migrationهای همین پروژه است؛ **یک process، صف کامل عملیات محلی و concurrency=1 در هر client**. ۵۰ handler هم‌زمان به معنی ۵۰ writer موازی SQL نیست.
- مدل **closed-loop**: هر کاربر در هر لحظه فقط یک آپدیت outstanding دارد، بدون think time. هر کاربر ۴ چرخهٔ ۲۵آپدیتی = ۱۰۰ آپدیت؛ ۵۰ کاربر مجموعاً ۵۰۰۰ آپدیت.
- نقش‌ها: ۱ مدیرکل، ۲۹ مدیر، ۱۰ اپراتور و ۱۰ مشاهده‌گر. مسیرها متناسب با نقش، شامل browse، جستجو/Back، سفارش تک‌قلمی و fulfilment/مرسوله‌اند؛ تمام حالت‌های همهٔ فرم‌ها workload بار نیستند و جداگانه تست شده‌اند.
- fixture: ۸ محصول و ۴۰ سفارش آماده برای fulfilment. ۱۲۰ سفارش تازه، ۴۰ تکمیل سفارش و ۲۴۰ رد مجوز قابل‌انتظار رخ می‌دهد. رد دسترسی صحیح، خطای ناخواسته یا سفارش موفق نیست.
- محدودکنندهٔ per-chat شبیه‌ساز **پیش از هر آپدیت reset می‌شود**. سقف واقعی Telegram/429، latency اینترنت، cold start، راه‌اندازی fixture و init از این نرخ نتیجه‌گیری نمی‌شوند.
- زمان هر sample از شروع تحویل update به pipeline تا پایان آن است؛ نه تا نمایش در دستگاه Telegram. latency کل شامل اکشن‌های خواندنی و ردهای سریع نیز هست؛ آن را latency ثبت سفارش تفسیر نکنید.

**محدودیت کارایی مشاهده‌شده:** event-loop delay صدک ۹۹ برابر **829.42 ms** است؛ با وجود صحت تمام داده‌ها، این اجرا نشان‌دهندهٔ latency یکنواخت یا مناسب‌بودن برای تولید پرترافیک نیست. برای Production باید lag/latency و سهمیهٔ شبکه را در staging و پیکربندی واقعی بسنجید، concurrency را تنظیم و در صورت نیاز صف/backpressure طراحی کنید.

RSS/heap شامل runtime، DB حافظه، log/session و تاریخچهٔ پاسخ‌های TestBot است؛ footprint هر کاربر Production از این نسبت محاسبه نمی‌شود. حافظه هر ۵۰ms نمونه‌برداری شده، پس اوج‌های بین نمونه‌ها ممکن است دیده نشوند. اندازهٔ session از ۲۰ نمونه است، نه scan تمام رکوردها و نه سقف سخت بایت. CPU با worker/native می‌تواند از مدت دیواری بیشتر باشد.

## تطبیق شواهد با سورس

گزارش، SHA-256 مستقل هر یک از **109 فایل** اجرایی/تست/SQL/metadata/config/lockfile و hash ترکیبی مسیر+بایت را دارد. README، مستندات، screenshot و گزارش generated خودشان در fingerprint اجرایی نیستند.

```text
aca15a7a0285810187ab7611da629dea131676435d3897e2b98d6a444bfa3404
```

الگوریتم در `sourceFingerprint` فایل `src/tests/helpers/stress-runner.ts` است: مرتب‌سازی مسیرها، سپس `path + NUL + bytes + NUL`. پس از تغییر سورس، گزارش قدیمی را شاهد نسخهٔ تازه ندانید؛ runner را دوباره اجرا کنید. این hash امضای ناشر یا زنجیرهٔ اعتماد مستقل نیست.

در CI، coverage با floor، full stress و build اجرا می‌شوند و گزارش بار artifact می‌شود؛ **اجرای remote CI در حساب شما ادعا نشده است**. `npm run check` همین gateهای اصلی را محلی اجرا می‌کند. [روش تست](TESTING.md) · [امنیت و مرز تضمین‌ها](../SECURITY.md) · [بررسی نهایی](VERIFICATION.md).
